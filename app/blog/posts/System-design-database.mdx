Database Categories
1. Relational Database (SQL)

Examples:

MySQL
PostgreSQL
Oracle Database
Microsoft SQL Server
Data Model
Users
+----+-------+
| id | name  |
+----+-------+

Orders
+----+---------+
| id | user_id |
+----+---------+

Relationships are enforced by foreign keys.

Good At
Strong consistency
Transactions (ACID)
Complex joins
Financial systems
Order systems
Inventory systems
Bad At
Horizontal scaling is harder
Schema changes can be expensive
Very large write throughput
Typical Use Cases
Banking
E-commerce
ERP
Payment systems
2. Document Database

Examples:

MongoDB
Couchbase
Data Model
{
  "userId": 123,
  "name": "John",
  "addresses": [
    {
      "city": "Seattle"
    }
  ]
}
Good At
Flexible schema
Fast development
JSON-native
Easy horizontal scaling
Bad At
Complex joins are weak
Data duplication common
Multi-document transactions less ideal
Typical Use Cases
User profiles
CMS
Product catalogs
AI application metadata
3. Key-Value Database

Examples:

Redis
Amazon DynamoDB
Data Model
user:123 -> {...}
Good At
Extremely fast
Millisecond latency
Massive scale
Bad At
Poor querying capability
Limited relationships
Typical Use Cases
Session storage
Cache
Shopping cart
User state
4. Wide-Column Database

Examples:

Apache Cassandra
Apache HBase
ScyllaDB
Good At
Massive write throughput
Multi-region deployments
Petabyte scale
Bad At
Limited joins
More complicated modeling
Typical Use Cases
Messaging
Event storage
Time-series workloads
5. Graph Database

Examples:

Neo4j
Amazon Neptune
Good At
Relationship traversal
Social graphs
Recommendation systems
Bad At
Expensive at huge scale
Not ideal for transactional workloads
Typical Use Cases
Friend relationships
Fraud detection
Knowledge graphs
6. Search Database

Examples:

Elasticsearch
OpenSearch
Good At
Full-text search
Ranking
Analytics
Bad At
Not source of truth
Eventual consistency
Typical Use Cases
Search bar
Log analysis
Product search
7. Vector Database

Examples:

Qdrant
Pinecone
Milvus
Good At
Semantic search
RAG
AI memory
Bad At
Not for transactional data
Not replacement for SQL
Typical Use Cases
ChatGPT-like RAG
AI agents
Similarity search
Quick Comparison Table
Database Type	Read	Write	Scale	Consistency	Best For
SQL	Good	Good	Medium	Strong	Orders, Payments
MongoDB	Good	Good	High	Medium	User Data
Redis	Excellent	Excellent	High	Medium	Cache
Cassandra	Good	Excellent	Excellent	Eventual	Messaging
Neo4j	Good	Medium	Medium	Strong	Social Graph
Elasticsearch	Excellent	Good	High	Eventual	Search
Vector DB	Similarity Search	Good	High	N/A	AI
What Does WeChat Use?
Chat Messages

A system like WeChat typically stores chat messages in a wide-column database similar to:

Cassandra-like systems
Proprietary distributed storage

Reason:

User A -> User B

Requirements:

Billions of messages
Sequential reads
Huge write volume
Multi-region replication

Typical key:

conversation_id
message_id
timestamp

Messages are usually stored append-only.

Friend Relationships

Often stored in:

Graph database concepts
Large distributed KV systems
user -> friend list
Search

Separate:

Elasticsearch/OpenSearch cluster
Cache

Separate:

Redis cluster

A large messaging platform almost never uses a single database.

What Does Telegram Use?

Telegram uses a custom distributed architecture.

Conceptually:

Data	Likely Storage Type
Messages	Distributed storage
User Profiles	SQL/KV
Sessions	Redis-like
Search	Search Index

Telegram optimized heavily for:

Fast writes
Multi-device sync
Global replication

System Design Interview Rule of Thumb

If the interviewer asks:

Orders / Payments
PostgreSQL
MySQL

Because consistency is critical.

User Profiles
MongoDB
PostgreSQL

Flexible schema.

Chat Messages
Cassandra
ScyllaDB
DynamoDB

Massive write throughput.

Search Bar
Elasticsearch
OpenSearch
Recommendation System
Neo4j
Graph DB
AI Agent / RAG
PostgreSQL + Qdrant

This combination is extremely common today:

PostgreSQL = source of truth
Qdrant = semantic retrieval
One Interview-Friendly Summary
SQL
├─ Strong consistency
├─ Transactions
└─ Orders / Payments

MongoDB
├─ Flexible schema
├─ Easy development
└─ User profiles

Redis
├─ Extremely fast
└─ Cache / Sessions

Cassandra
├─ Massive writes
├─ Horizontal scaling
└─ Chat messages

Elasticsearch
├─ Full-text search
└─ Search engine

Neo4j
├─ Relationship queries
└─ Social graph

Qdrant
├─ Vector search
└─ RAG / AI applications

For most modern large-scale systems, the winning answer in interviews is usually polyglot persistence: use multiple databases, each for the workload it handles best, rather than trying to store everything in MongoDB or everything in PostgreSQL.
